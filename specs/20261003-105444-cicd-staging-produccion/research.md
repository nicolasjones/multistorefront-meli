# Research: CI/CD staging → producción para migraciones, VPS, flows y dashboards

**Feature**: `specs/20261003-105444-cicd-staging-produccion/spec.md`

Este research resuelve, a nivel técnico, las dos preguntas que el assessment dejó abiertas (conectividad del runner, existencia de proyectos cloud) y las decisiones de diseño necesarias para implementar las cuatro piezas del alcance, reutilizando al máximo el código y los patrones ya existentes en el repo.

## 1. Conectividad del runner self-hosted hacia el VPS real

- **Decision**: El job de deploy a VPS no necesita que el runner *sea* el VPS ni que esté en la misma red local. Controla el Docker del VPS remotamente seteando `DOCKER_HOST=ssh://<usuario>@<host>` antes de invocar `pnpm deploy:vps -- <entorno>` — `scripts/deploy-vps.mjs` ya invoca el binario `docker` local vía `operaciones.mjs#run()`, que hereda `process.env` sin cambios de código; el CLI de Docker ya soporta `DOCKER_HOST=ssh://...` de forma nativa.
- **Rationale**: Reutiliza exactamente el patrón de acceso que ya usa el repo para despacho remoto — `docs/deployment.md` documenta una clave SSH privada en Base64 (`SECRET_ORQUESTACION_SSH_PRIVATE_KEY`, spec 014) para que Kestra despache workers a servidores de organización por SSH. El mismo mecanismo (clave privada como secret, decodificada a un archivo temporal al iniciar el job) resuelve la conectividad del runner sin exigir que el runner migre de máquina ni que se abra ningún puerto nuevo del VPS más allá del SSH que ya usa el operador para la copia manual de hoy.
- **Alternatives considered**: (a) Migrar el runner self-hosted para que corra físicamente en el VPS — descartado: acopla el CI a la disponibilidad del VPS y contradice que hoy el runner es compartido entre varios productos derivados en la máquina de desarrollo (`docs/deployment.md`, sección de réplicas). (b) Abrir la API de Docker por TCP con TLS en el VPS — descartado: mayor superficie de ataque que SSH, y el VPS ya tiene `sshd` configurado (`docs/deployment.md`, "Servidores de organización").
- **Resuelve**: la pregunta abierta de `spec.md` sobre conectividad — no requiere aprovisionar nada nuevo en el VPS (ya tiene `sshd`); sólo requiere agregar el cliente SSH a la imagen del runner (`infra/runner/Dockerfile` no lo instala hoy) y una clave SSH por entorno como secret.
- **Corrección (T025, validación real)**: a diferencia de `SECRET_ORQUESTACION_SSH_PRIVATE_KEY` (spec 014), `VPS_SSH_PRIVATE_KEY` se guarda como texto plano PEM, **sin** Base64 — los secrets de GitHub Actions ya soportan multilínea nativamente, y el intento original de `base64 -d` falló contra la clave real con `base64: invalid input` (el secret configurado era el PEM crudo, no una versión codificada). Se corrigió el workflow para escribir el secret directo al archivo en vez de decodificarlo.

## 2. Credenciales del deploy de infraestructura sin archivo `.env` en el VPS

- **Decision**: El workflow sintetiza un archivo `.env.<entorno>` transitorio en el **workspace efímero del job de CI** (no en el VPS) a partir de los secrets del GitHub Environment correspondiente, justo antes de invocar `pnpm deploy:vps -- <entorno>`, y lo descarta al terminar el job. `scripts/deploy-vps.mjs` no necesita reescritura: sigue recibiendo un `--env-file` válido, solo que ya no vive en el filesystem persistente del VPS ni se edita a mano por SSH.
- **Rationale**: Cumple el requisito (FR-006) con el cambio de superficie mínimo — cero reescritura del script ya probado, cero riesgo de romper el flujo manual que algún operador todavía use localmente contra un VPS de prueba. El archivo nunca se commitea (el workspace del runner se descarta por job) y nunca se persiste en el disco del VPS.
- **Alternatives considered**: Reescribir `deploy-vps.mjs` para leer cada variable individualmente desde `process.env` y generar el `--env-file` internamente — descartado por ahora: agrega superficie de parsing/validación al script sin beneficio real sobre sintetizar el archivo en el step del workflow, que ya es el patrón estándar de GitHub Actions para "env desde secrets". Queda documentado como alternativa si en el futuro se necesita invocar el script fuera de un workflow de GitHub Actions.
- **Corrección (T025, validación real)**: el nombre `VPS_DEPLOY_ENV` se confundió con "elegir el entorno" (`staging`/`production`) en vez de "el contenido del `.env`" — se configuró el secret con el valor literal `staging`. Dos consecuencias: (1) `docker compose` no falla fuerte con un `.env` mal formado (variables faltantes quedan vacías silenciosamente), así que el error real aparece recién en `build`/`up`, no en `config`; (2) como el valor del secret coincidía con una palabra común (`staging`), GitHub enmascaró esa palabra en *todo* el log del job, incluyendo texto estático no relacionado — lección general: evitar que un secret tenga como valor una palabra que también aparezca en mensajes de error o nombres de pasos. Mitigado agregando una validación explícita (cuenta de líneas `CLAVE=valor`) antes de usar el archivo, que falla con un mensaje claro sin depender de contenido enmascarable.
- **Corrección 2 (T025, validación real contra el VPS real)**: con las credenciales ya corregidas, Kestra se desplegó exitosamente contra el VPS real de staging, pero Superset falló con `IsADirectoryError: [Errno 21] Is a directory: '/app/pythonpath/superset_config.py'`. Primer intento de causa (`--project-directory` ausente, distinto default entre versiones de Compose) — **descartado**: fijar `--project-directory` no resolvió el error real; era un síntoma correlacionado, no la causa.
- **Corrección 2, causa real (T025)**: es arquitectural, no de Compose. `DOCKER_HOST=ssh://usuario@host` hace que el **cliente** `docker compose` (local, en el runner de CI) hable con el **daemon remoto** del VPS vía la API de Docker. Para un bind mount (`./superset_config.py:/app/pythonpath/...`), el cliente solo envía al daemon la ruta ABSOLUTA ya resuelta como string — quien efectivamente crea el mount es el daemon, usando ESE string contra SU PROPIO filesystem. La ruta resuelta en el runner de GitHub Actions (`/home/runner/_work/.../infra/superset/superset_config.py`) no existe en el VPS; Docker, ante un bind source inexistente, crea un directorio vacío ahí en vez de fallar — de ahí el `IsADirectoryError`. El `build` de la imagen (que sí funcionó, incluyendo para Superset) no tiene este problema porque el contexto de build se transmite completo al daemon remoto vía la misma API — es un mecanismo distinto al de los bind mounts. Kestra/Nango/Playwright nunca mostraron este síntoma porque ninguno de los tres usa bind mounts relativos (solo volúmenes nombrados, que Docker crea y gestiona él mismo en el lado del daemon, y en el caso de Kestra un bind absoluto a `/var/run/docker.sock`, que existe con esa misma ruta en cualquier host Linux).
- **Decision**: hornear los tres archivos de configuración de Superset (`superset_config.py`, `crear_cuenta_servicio_guest_token.py`, `configurar_embebido.py`) en la imagen vía `COPY` en `infra/superset/Dockerfile`, en vez de bind-montearlos desde `compose.yaml`. Evaluadas tres alternativas (ver abajo); esta es la más chica y la que no revierte una decisión de diseño ya validada en producción real (Kestra).
- **Alternatives considered**: (a) Dejar de usar `DOCKER_HOST=ssh` para `up`/`build` y en cambio copiar el repo al VPS (`rsync`/`scp`) y ejecutar `docker compose` dentro de una sesión SSH remota, igual que el proceso manual ya usa — descartado para esta spec: revierte la decisión central de `research.md` §1 (ya validada con Kestra funcionando de punta a punta en el VPS real), reintroduce la complejidad de sincronizar el checkout al VPS (que esta spec buscaba evitar), y sería una reescritura de los tres workflows, no un fix acotado — si en el futuro otro producto necesita bind mounts relativos de forma más general, revisar esta alternativa. (b) Hornear los archivos (elegida). (c) Seguir bind-monteando pero resolviendo la ruta contra el filesystem del VPS en vez del del runner — descartada: requeriría que el runner conozca la estructura de directorios del VPS, acoplamiento que la spec evitó deliberadamente en `research.md` §1-2.
- **Nota general**: cualquier archivo que un producto necesite disponible dentro del contenedor y que hoy se bind-montee con ruta relativa desde `compose.yaml` tiene este mismo problema con `DOCKER_HOST=ssh` remoto. Un producto derivado que agregue un quinto servicio a `deploy-vps.mjs` con ese patrón debe hornear sus archivos en la imagen (opción b) en vez de bind-montearlos, o ese servicio no podrá desplegarse por este mecanismo.
- **Corrección 3 (T025, validación real de producción)**: con Superset corregido, Kestra y Superset se desplegaron exitosamente contra producción real — pero el deploy de Playwright chocó con `Bind for 127.0.0.1:3103 failed: port is already allocated`, contra una instancia dedicada real de un cliente (ya corriendo en ese mismo puerto del VPS, levantada a mano esa misma noche). Causa de fondo: **Playwright no es un producto de plataforma compartido** como Kestra/Superset/Nango — cada cliente corre su propia instancia dedicada, nunca una central. Esta decisión ya estaba tomada y documentada en el producto derivado (no es nueva de esta spec); `docs/architecture.md` del propio template ya dejaba la topología de producción de Playwright explícitamente como pregunta abierta ("la dirección exacta con la que un flow alcanza este servicio... queda por resolver cuando se escriba el primer flow real que lo use — es una decisión de ese flow, no de esta pieza de infraestructura"). El loop de `scripts/deploy-vps.mjs` nunca debió incluirlo junto a los productos sí compartidos.
- **Decision**: sacar `'playwright'` del array de productos que recorre `scripts/deploy-vps.mjs`; sacar `infra/playwright/compose*.yaml` de los `paths` que disparan `deploy-infraestructura-vps.yml`; borrar `infra/playwright/compose.vps.yaml` (la variante de despliegue centralizado al VPS, ya no aplica — `infra/playwright/compose.yaml` se conserva intacto para desarrollo local, `pnpm dev:playwright`, que no cambia).
- **Alternatives considered**: ninguna — no es una decisión de diseño nueva de esta spec, es corregir que el mecanismo genérico adoptó por error una topología (Playwright compartido) que el propio template ya había dejado explícitamente sin resolver, y que el producto derivado ya resolvió en sentido contrario.
- **Corrección 4 (T025, validación real de producción)**: con Playwright fuera del loop, Kestra y Superset siguieron sanos y el deploy llegó a Nango — pero chocó con `Conflict. The container name /platform-production-nango-nango-db-1 is already in use by container <hash>`. Inspeccionado el contenedor en conflicto: mismo timestamp, mismas labels de Compose del mismo proyecto que la corrida que estaba fallando — no es un recurso preexistente de un deploy manual anterior. Causa real: una condición de carrera de Docker Compose al crear en paralelo servicios sin `depends_on` entre sí (`nango-db` y `nango-redis` no dependen uno del otro en `infra/nango/compose.yaml`, así que Compose los crea simultáneamente y a veces un `create` choca contra el propio contenedor que la misma corrida recién terminó de crear).
- **Decision**: envolver el paso `docker compose up` de `scripts/deploy-vps.mjs` en un reintento acotado — si falla con un mensaje que matchea `/already in use|Conflict\. The container name/i`, reintenta una vez más (el segundo intento encuentra el contenedor ya creado por el primero y lo reconcilia en vez de competir de nuevo por crearlo); cualquier otro error sigue sin reintentarse. Requirió una variante local de `run()` (`dockerComposeUp`) que mantiene el progreso visible en vivo (como ya lo tenía `run()` sin `quiet`) pero además captura `stderr` para poder inspeccionar el mensaje — `run()` en modo no silencioso usa `stdio: 'inherit'`, que no permite inspeccionar nada desde Node, y en modo `quiet` descarta `stdout` por completo (se perdería el progreso de creación de contenedores que ya fue clave para diagnosticar varios de los hallazgos anteriores de T025).
- **Alternatives considered**: (a) `--no-deps` o reordenar manualmente los servicios en `compose.yaml` para serializar su creación — descartado: cambia el compose file de cada producto para trabajar alrededor de un comportamiento de Compose, en vez de manejarlo una sola vez en el mecanismo genérico que ya envuelve todos los `docker compose up`. (b) Reintentar el `up` (elegida) — acotado al propio script de deploy, cubre cualquier producto futuro con el mismo patrón de servicios independientes. (c) Reintentar con backoff/varias veces — descartado por ahora: un solo reintento ya resolvió el caso real observado; agregar más no tiene evidencia que lo justifique.

## 3. Migraciones de Supabase contra proyectos cloud

- **Decision**: Nuevo script `scripts/migrar-supabase-cloud.mjs`, que ejecuta `supabase db push --db-url "$SUPABASE_DB_URL"` contra la cadena de conexión Postgres del proyecto cloud del entorno (un secret por entorno: `SUPABASE_DB_URL` dentro del GitHub Environment de staging y, por separado, dentro del de producción), sin usar `supabase link` ni un access token de cuenta.
- **Rationale**: Una cadena de conexión acotada a la base de ese proyecto es menos privilegio que un Personal/Service Access Token de la cuenta de Supabase (que puede administrar todos los proyectos de la organización) — alineado con el principio de aislamiento del propio repo. `supabase db push --db-url` no requiere `supabase link` (que persiste estado local de "proyecto vinculado"), lo que mantiene el job sin estado entre corridas.
- **Alternatives considered**: `supabase link --project-ref <ref>` + `supabase db push` autenticado con `SUPABASE_ACCESS_TOKEN` — descartado como opción primaria por el alcance más amplio del token (administra toda la cuenta); documentar como alternativa si el DB password rota con demasiada frecuencia como para mantenerlo como secret estático.
- **Limitación conocida (T025, validación real)**: el job `staging` de `migraciones-cloud.yml` corrió dos veces contra el `SUPABASE_DB_URL` real configurado (el proyecto staging real de `estudio-contable-automation`, producto derivado) y falló las dos con `Remote migration versions not found in local migrations directory`. Causa: ese proyecto tiene aplicado el historial de migraciones del **producto derivado** (superset de lo que trae esta plantilla, con migraciones propias del negocio), que no coincide con `supabase/migrations/` de **este** repo (la plantilla genérica) — `supabase db push` rechaza avanzar ante un historial remoto que no reconoce, exactamente la protección de seguridad que se espera que tenga. No es un bug de `migrar-supabase-cloud.mjs` ni del workflow: la conexión, autenticación y el CLI de Supabase funcionaron correctamente — recibieron y mostraron una respuesta real y correcta del proyecto real. **Decisión**: se documenta como limitación conocida de validar el mecanismo genérico de la plantilla contra credenciales reales de un producto derivado, no se corrige apuntando esta validación a un proyecto Supabase dedicado del propio template. Razón: la plantilla no es dueña de ningún proyecto Supabase cloud real por diseño (ver `spec.md` → Assumptions); crear uno solo para esto introduciría un recurso cloud persistente adicional a mantener, cuando la corrección de migraciones contra el contenido exacto de `supabase/migrations/` de este repo ya está cubierta por el job `database` de `validate.yml` (CI local aislado, mismas migraciones, de punta a punta). Lo que T025 necesitaba validar de este mecanismo — que el workflow dispara, resuelve el secret, invoca `supabase db push` contra un endpoint real, y reporta el resultado real sin ambigüedad — ya quedó demostrado por este mismo fallo.

## 4. Publicación de flows de Kestra dentro del mismo pipeline

- **Decision**: Cero cambios de código en `infra/kestra/desplegar-flow.mjs` — ya acepta credenciales por variable de entorno (`KESTRA_BASIC_AUTH_USERNAME`/`PASSWORD`) y por flags (`--kestra-url`). El workflow nuevo solo necesita invocarlo dos veces (staging, producción) con el mismo gate, pasando la URL y las credenciales del Environment correspondiente.
- **Rationale**: Es, de las cuatro piezas, la que menos trabajo de implementación requiere — el research de la fase de assessment ya identificó que este script es el más cercano a ser CI-friendly.
- **Alternatives considered**: ninguna — no hay decisión de diseño pendiente aquí, solo wiring.

## 5. Wrapper genérico de import de dashboards de Superset

- **Decision**: Nuevo script `infra/superset/importar-dashboards.mjs`, mismo patrón que `desplegar-flow.mjs` (fetch directo a la API REST de Superset, sin SDK), que recibe `--source <ruta-al-paquete-exportado>` y `--entorno <staging|production>`, resuelve la URL y credenciales del Superset de ese entorno desde variables de entorno, y llama al endpoint de import de Superset.
- **Rationale**: Reutiliza la arquitectura "script Node + fetch + credenciales por entorno" ya validada por `desplegar-flow.mjs`, en vez de introducir una dependencia nueva (SDK de Superset o su CLI empaquetada en Python). Un detalle técnico corrige una imprecisión menor de FR-010: Superset no exporta un YAML suelto por dashboard, exporta un paquete (ZIP) que contiene el YAML del dashboard junto con los YAML de los datasets/bases que usa — el wrapper documenta y acepta ese formato de paquete, consistente con "YAMLs de dashboards" en sentido amplio (son YAML, empaquetados).
- **Alternatives considered**: Empaquetar el CLI `superset import-dashboards` (Python) dentro del runner — descartado: agrega una dependencia de Python al runner (hoy Node/Docker CLI únicamente) solo para esta pieza, cuando la API REST cubre el mismo caso sin dependencias nuevas.
- **Confirma** (research de assessment): no hay ningún caso de uso real contra el que probar el wrapper hoy — se valida con un paquete de ejemplo/sintético durante la implementación, tal como ya quedó documentado en `spec.md` → Assumptions.

## 6. Mecanismo de gate compartido (staging → producción)

- **Decision (original, intake)**: Cada uno de los tres workflows automáticos (migraciones, deploy de infraestructura, publicación de flows) define dos jobs en el mismo archivo: `staging` (dispara en push, sin gate) y `production` (`needs: staging`, `environment: <nombre>-production` con required reviewers configurado en GitHub). No se introduce ninguna Action ni script de aprobación custom.
- **Rationale (original)**: Ya hay precedente exacto en el propio repo — `.github/workflows/worker-images.yml` ya usa `environment: worker-images-production`, aunque en un solo job (no necesita gate de dos fases porque no hay "staging" de una imagen). Esta spec generaliza ese mismo mecanismo a un segundo job con `needs`.
- **Alternatives considered (original)**: ninguna — era una decisión ya tomada por el coordinador en el intake (no rediseñar).

### Revisión (post-implementación, decisión del coordinador — ver `tasks.md` T027)

- **Hallazgo**: la regla de protección "required reviewers" en GitHub Environments requiere un plan de pago (Team/Enterprise) para repositorios privados, o que el repositorio sea público. Verificado contra la API real: tanto el fork (`nicolasjones/automation-platform-template`) como el repo de la organización (`Agenmatica/automation-platform-template`) estaban en plan Free y el intento de crear la regla devolvía `422`. Ambos repos se hicieron públicos para desbloquear el PR; aun así, el coordinador decidió no depender de required reviewers como mecanismo central — ver próxima decisión.
- **Decision (revisada)**: `production` deja de usar `needs: staging` + required reviewers. Pasa a dispararse exclusivamente por `workflow_dispatch` (alguien entra a la pestaña Actions y lo corre a propósito). `staging` sigue disparando solo por `push`. Los GitHub Environments se conservan — siguen separando los secrets de cada entorno, que no depende de ninguna regla de pago — solo se cae el campo de reviewers requeridos.
- **Rationale (revisada)**: es la alternativa sin costo que preserva la intención original (producción no se despliega sola; alguien tiene que decidirlo activamente) sin depender de una función de plan de pago. No requiere ninguna Action ni script custom — `workflow_dispatch` es un trigger nativo de GitHub Actions.
- **Alternatives considered (revisada)**: (a) pagar GitHub Team/Enterprise para mantener required reviewers — descartado por costo; (b) un script/Action de aprobación custom (p. ej. comentario en un issue) — descartado, contradice la regla del propio `CLAUDE.md`/intake de "nativo de GitHub, no hay que construir nada custom"; `workflow_dispatch` sigue siendo 100% nativo.
- **Trade-off aceptado**: sin `needs`, nada impide disparar `production` para un commit cuyo `staging` nunca corrió o falló — la responsabilidad de verificar eso antes de tocar "Run workflow" queda en la persona que lo dispara, no en el YAML. Documentado en `contracts/workflow-gate.md` → Edge cases.

### Revisión 2 (bug `gate-migraciones-stg-prd`, 2026-10-05) — el trade-off aceptado causó un incidente real

- **Hallazgo**: el 2026-10-04, un `workflow_dispatch` contra `production` en un producto derivado (`estudio-contable-automation`, repo **privado**) aplicó 81 migraciones de golpe a producción, incluidas 3 funcionalidades de IA recién creadas, sin que nadie hubiera validado feature por feature que ya habían pasado por staging. Exactamente el trade-off que la Revisión 1 documentó como aceptado, materializado.
- **Por qué "hacer público el repo" (la solución de la Revisión 1 para desbloquear required reviewers) no alcanza**: desbloquea required reviewers gratis en el repo donde se hizo — el template. Pero el template no es donde corre este workflow contra datos reales; los **productos derivados** sí, y son privados por diseño (contienen lógica de negocio y, eventualmente, credenciales/config específicas de clientes reales — no hay ninguna razón para hacerlos públicos solo para desbloquear esta feature, y hacerlo tendría costos de exposición mucho mayores que el problema que resuelve). Cualquier remediación que dependa de visibilidad pública del repo no se porta al caso que realmente importa.
- **Decision (revisada otra vez)**: gate técnico sin requisito de plan de pago ni de visibilidad del repo. Nuevo script `scripts/verificar-staging-exitoso.mjs`, primer step de todo job `production` en los tres workflows: consulta `GET /repos/{repo}/actions/workflows/{workflow}/runs?branch=main&event=push&status=success` vía la API de GitHub Actions (con el `GITHUB_TOKEN` por defecto del job, que ya existe sin configurar ningún secret nuevo) y exige que exista un run con `head_sha` igual al commit que `production` está por promover. Si no existe, falla antes de instalar nada o de resolver cualquier secret de producción.
- **Rationale**: funciona igual en el template (público) y en cualquier producto derivado (privado) — no depende de ninguna feature de plan pago de GitHub. Reutiliza `GITHUB_TOKEN`, que todo job de Actions ya recibe automáticamente (solo hace falta declarar `permissions: actions: read` para que alcance a leer runs). No introduce ninguna Action de terceros ni script de aprobación custom más allá de lo que ya es el patrón del repo (scripts Node en `scripts/`, mismo criterio que `migrar-supabase-cloud.mjs`/`validar-migraciones-aditivas.mjs`).
- **Alternatives considered**: (a) Required reviewers en el Environment de producción del template público — sigue siendo válido como defensa adicional *ahí*, documentado como alternativa complementaria, pero no reemplaza el gate técnico porque no se porta a productos derivados privados. (b) Pagar GitHub Team/Enterprise en cada producto derivado para habilitar required reviewers — descartado por costo, mismo motivo que la Revisión 1 original. (c) Chequear además, específicamente en `migraciones-cloud.yml`, que las migraciones a aplicar ya aparezcan como aplicadas en el historial de staging (`supabase migration list --db-url <staging>`) — evaluado como defensa en profundidad adicional, no implementado en esta revisión por requerir exponer el `SUPABASE_DB_URL` de staging (de solo lectura) al Environment de producción, lo que diluye el aislamiento de credenciales entre entornos; queda abierto para una spec futura si el chequeo por `head_sha` resulta insuficiente en la práctica.
- **Trade-off aceptado (nuevo, más chico)**: el chequeo confirma que `staging` *corrió y terminó en verde* para ese commit exacto — no reemplaza el juicio humano de si eso implica que la funcionalidad está lista para producción (una migración puede aplicar sin error y la feature igual no estar lista para habilitarse a clientes reales). Documentado en `contracts/workflow-gate.md` → Edge cases.
