# Implementation Plan: Ventas y despacho · Ventas avisos de faltantes

**Spec**: `specs/20261110-100000-ventas-avisos-de-faltantes/spec.md` · **Épica**: MSF-161 · **Rama**: `epic/MSF-161-ventas-y-despacho-ventas-avisos-de-faltantes`

## Resumen

Dos historias sobre lo ya entregado por F-VTA-18 (`dominio.faltantes_venta`, `/ventas/faltantes`) y F-STK-17 (cola de avisos, Edge Function y flow): avisar a los clientes con faltantes eligiendo y editando el texto (F-VTA-26) y marcar «Para avisar» al registrarse un ingreso de mercadería (F-VTA-27). El plan es **reutilizar la cola `dominio.faltantes_avisos`, la Edge Function `enviar-aviso-faltante` y el flow `avisos-faltantes`** y agregar solo columnas, una RPC, un disparador y la UI. Detalle de qué se reutiliza, qué se agrega y por qué: spec › *Relación con F-STK-17 y F-VTA-18*.

## Diseño por historia

### F-VTA-26 · Avisar a clientes con faltantes

- **Cola**: `alter table dominio.faltantes_avisos add column if not exists mensaje text check (mensaje is null or length(mensaje) <= 1000)`. `private.faltante_abierta(uuid)` suma la rama «fila abierta en `faltantes_venta` de esa línea» (`join comprobantes_venta_lineas l on l.comprobante_id = f.comprobante_id and l.orden = f.linea_orden`). `tomar_aviso_faltante(uuid, integer)` mantiene firma y `returns table (cliente, correo, lineas)`: cada elemento de `lineas` suma `mensaje`; `cantidad` = `cantidad_faltante` si hay faltante de venta abierto, si no `l.cantidad`; y toma solo las líneas del cliente con el mismo `mensaje` que la más antigua pendiente (`is not distinct from`), el resto sale en el barrido siguiente (nunca dos correos con textos mezclados). Sin cambio de firma → sin `drop` (guard de firmas).
- **RPC** `public.avisar_faltantes_venta(p_ids uuid[], p_mensaje text default null, p_reavisar boolean default false) returns jsonb` (`security definer`, `search_path = ''`, `revoke … from public, anon` + `grant … to authenticated`): exige sesión y `private.nivel_seccion('ventas') = 'edicion'` (`42501`); valida 1…200 ids (`22023`) y `p_mensaje` (recortado, ≤ 1.000, vacío → nulo); recorre los ids ordenados; por cada faltante `abierto` de la organización: permiso por tienda (`nivel_ventas_en_empresa(empresa) = 'edicion'`, si no `sin_permiso`) → cliente sin correo (`sin_correo`) → estado de cola (`en_cola` si `pendiente`, `ya_avisado` si `enviado` y no `p_reavisar`) → `insert … on conflict (linea_id) do update` reiniciando la fila (estado `pendiente`, intentos 0, `ultimo_error` nulo, `enviado_en` nulo, `created_at`/`updated_at` = now, `mensaje`) cuando está `agotado` o `enviado` con `p_reavisar`. Lo que no es abierto o no existe en la organización → `no_abierto` (misma respuesta: no delata). Actividad `ventas.faltantes_avisados` (cantidad y clientes, sin correos). Devuelve `{encolados, lineas_avisadas, omitidos_ya_avisados, omitidos_en_cola, omitidos_sin_correo, omitidos_sin_permiso, omitidos_no_abiertos, detalle: [{id, resultado}]}`.
- **Listado** `public.listar_faltantes(p_empresa_id, p_pagina, p_tamano, p_aviso text default null)`: `drop function public.listar_faltantes(uuid, integer, integer)` + alta con la firma nueva (mismo `returns table` + `aviso text`, `aviso_en timestamptz`), `left join dominio.faltantes_avisos a on a.linea_id = l.id` (con `l` = línea por `(comprobante_id, orden)`); `aviso` = `avisado` si `a.estado in ('pendiente','enviado')`, si no `sin_avisar`; `aviso_en = coalesce(a.enviado_en, a.created_at)` si avisado. `p_aviso` ∈ {null, `sin_avisar`, `avisado`} (otro valor → `22023`). Un solo `drop`/`create`, `revoke`/`grant` explícitos. El pgTAP existente que nombra la firma vieja se actualiza (T005).
- **Edge Function**: `contenido.ts` — `LineaFaltante` suma `mensaje?: string | null`; `cuerpoAviso` arma `Hola <cliente>,` + (`mensaje` saneado | frase por defecto de F-STK-17) + lista de productos (+ cierre por defecto solo sin mensaje). Saneamiento: quita caracteres de control salvo salto de línea, colapsa más de dos saltos, recorta a 1.000; texto plano. `handler.ts` solo ajusta el tipo `Tomado`. El flow YAML no cambia.
- **UI**: `lib/ventasFaltantes.ts` suma el tipo `AvisoFaltante`, los campos `aviso`/`aviso_en`, `TEXTO_AVISO_POR_DEFECTO`, `avisarFaltantesVenta(ids, mensaje, reavisar)` (validación 1…200, errores en castellano, nunca técnicos) y `mensajeResultadoAvisoVenta` (reutiliza el estilo de `mensajeResultadoAviso` de `lib/faltantes.ts` y agrega «El cliente no tiene correo»). `hooks/useListarFaltantes.ts` suma la selección atada al ámbito (patrón de `useFaltantes`). `pages/ventas/faltantes.tsx` suma la columna de casillas (solo `ventas` `edicion`), la columna Aviso (`EtiquetaEstado`: «Sin avisar» neutral, «Avisado · dd/mm» éxito), pie de selección, botón, diálogo con `TextField` multilínea (contador 1.000), casilla de reaviso, snackbar y refetch.
- **Reversión**: `drop function public.avisar_faltantes_venta(uuid[], text, boolean)`; restaurar `listar_faltantes` (`20270112130300`), `private.faltante_abierta` y `tomar_aviso_faltante` (`20261213100200`); `alter table dominio.faltantes_avisos drop column mensaje` (solo si no hay avisos con mensaje o tras exportarlos); revertir `contenido.ts`.

### F-VTA-27 · «Para avisar» al ingresar mercadería

- **Datos**: `alter table dominio.faltantes_venta add column if not exists para_avisar_en timestamptz, add column if not exists para_avisar_ingreso_id uuid references dominio.ingresos_mercaderia (id) on delete set null`; índice parcial `(organizacion_id, producto_id, creado_en, id) where estado = 'abierto' and para_avisar_en is null` para la cobertura. `check` opcional: `para_avisar_ingreso_id is null or para_avisar_en is not null`.
- **Disparador**: `private.marcar_faltantes_para_avisar()` (`security definer`, `search_path = ''`, `trigger`) y `create trigger ingresos_mercaderia_lineas_marcar_faltantes after insert on dominio.ingresos_mercaderia_lineas for each row`. Algoritmo (spec decisión 5): saldo = `new.cantidad`; `for f in select … from dominio.faltantes_venta f where f.organizacion_id = new.organizacion_id and f.producto_id = new.producto_id and f.estado = 'abierto' and f.para_avisar_en is null and not exists (select 1 from dominio.faltantes_avisos a join dominio.comprobantes_venta_lineas l on l.id = a.linea_id where l.comprobante_id = f.comprobante_id and l.orden = f.linea_orden and a.estado in ('pendiente','enviado')) order by f.creado_en, f.id for update` → si `f.cantidad_faltante <= saldo` marca y descuenta, si no `exit`. Todo dentro de `begin … exception when others then raise warning` (el ingreso no se rompe: FR-105). Actividad `ventas.faltantes_para_avisar` con la cantidad marcada (no se llama a `registrar_actividad` si no marcó nada). No toca `faltantes_avisos` (FR-101: «sin enviar nada»).
- **Listado**: `create or replace function public.listar_faltantes(uuid, integer, integer, text)` (misma firma que F-VTA-26): `aviso` suma `para_avisar` cuando `para_avisar_en is not null` y no está avisado (`aviso_en = para_avisar_en`); `p_aviso` acepta `para_avisar`; con ese filtro, `order by desde asc, id`.
- **UI**: filtro «Para avisar» (Todos · Para avisar, mismo patrón de filtro por estado que `pages/stock/list.tsx`) en `pages/ventas/faltantes.tsx`, chip «Para avisar» (variante de aviso informativo) y `useListarFaltantes` con `aviso` en el ámbito/reinicio de la lista.
- **Reversión**: `drop trigger ingresos_mercaderia_lineas_marcar_faltantes on dominio.ingresos_mercaderia_lineas; drop function private.marcar_faltantes_para_avisar();` restaurar `listar_faltantes` de F-VTA-26; `alter table dominio.faltantes_venta drop column para_avisar_ingreso_id, drop column para_avisar_en` (las marcas son una sugerencia, no historial).

## Riesgos

- **El «aviso» de F-VTA-26 es derivado de la cola**: si F-STK-17 cambia su semántica (p. ej. un estado nuevo en `faltantes_avisos`), `listar_faltantes` y `avisar_faltantes_venta` deben seguirla; las dos usan la misma expresión (`estado in ('pendiente','enviado')`) y el pgTAP la fija.
- **Concepto doble de faltante** (F-STK-17 vs F-VTA-18): documentado; la línea compartida usa una sola fila de cola.
- **Disparador sobre `ingresos_mercaderia_lineas`**: bloque de excepción para no romper el ingreso; el error queda en el log del servidor. Si `registrar_ingreso_mercaderia` se reescribe en otra épica, el disparador sigue valiendo (no depende de su firma).
- **Cambio de firma de `listar_faltantes`**: el guard de firmas del flujo exige actualizar los tests con la firma vieja (T005); las llamadas del navegador por nombre siguen funcionando (parámetro nuevo con valor por defecto).
- **Migraciones renumeradas por el flujo**: los nombres de arriba son indicativos; los tests y `plan.md` no deben leer migraciones por ruta.
- **Correo real**: el envío SMTP lo verifica la tarea de seguimiento `verificacion-externa` ya existente de F-STK-17 (MSF-532); acá se prueba hasta la cola y el handler con SMTP simulado.
